# Decisions

Append-only log. Format: date — decision — why.

- 2026-10-26 — Plain Drupal 11.4 core (recommended-project), not Drupal CMS — dashboard app, lean base shows architecture.
- 2026-10-26 — Custom content entities, not nodes — operational data, stronger showcase.
- 2026-10-26 — AI only summarizes; detection is deterministic PHP — reliable results, testable.
- 2026-10-28 — Agent auth: shared secret per site, HMAC of timestamp + path, 5-minute window — simple and secure, no OAuth on client sites.
- 2026-10-28 — `hm_agent` supports `^10.3 || ^11`, core-only deps — clients may still be on D10.
- 2026-10-28 — Upgrade Status is a data source, not a competitor — agent forwards its results when installed.
- 2026-10-28 — AGENTS.md is the single instruction file; CLAUDE.md imports it — Codex and Claude share one source of truth.
- 2026-10-28 — Local dev with DDEV (not MAMP) — reproducible stack for reviewers, CI and AI agents.
- 2026-10-28 — Host on Railway at health-monitor.tofdev.com, Dockerfile build, MariaDB service (superseded below), existing Railway account with CI/CD.
- 2026-10-28 — CI/CD: GitHub Actions + Railway autodeploy with Wait for CI; `drush deploy` as pre-deploy command — failed checks never reach production.
- 2026-10-28 — Database: MySQL 8.4 LTS instead of MariaDB, locally (DDEV) and on Railway — owner's usual stack, same as Acquia; 8.0 is past end of life.
- 2026-10-28 — Railway image is a single container (PHP-FPM + nginx), built from the repo Dockerfile; cron runs as a second Railway service from the same image with a different start command — simplest topology Railway supports well, avoids a separate web-server image to maintain.
- 2026-10-28 — First deploy installs from config/sync via `drush site:install --existing-config`; every later deploy runs `drush deploy` — standard Drupal CI/CD pattern, idempotent.
- 2026-10-28 — Railway project/services provisioned with the `railway` CLI, not the dashboard, where possible (project, app/MySQL services, variables, volume, domain) — repeatable, scriptable; only Pre-Deploy Command and Wait for CI have no CLI equivalent and stay dashboard-only.
- 2026-10-28 — GitHub repo made public — Railway's GitHub App wasn't deploying from the private repo (no webhook fired on push despite the service being linked); flipping to public plus reconnecting the service source unblocked it. No secrets were ever committed (verified via git history before flipping), so the exposure is just source code.
- 2026-10-28 — Railway domains must have their target port explicitly set to 8080 — both the generated `*.up.railway.app` and the custom `health-monitor.tofdev.com` domain defaulted to port 80 on creation, not the Dockerfile's `EXPOSE 8080`, causing the stock nginx default page to be served instead of Drupal. `docker/entrypoint.sh` also now removes `/etc/nginx/sites-enabled/default` at container start as a second layer of defense.
- 2026-11-03 — Agent requests use `X-HM-Timestamp` and `X-HM-Signature`; the HMAC-SHA256 message is the timestamp, a newline, and the request path, with a 300-second past-only window. Client secrets live in `$settings['hm_agent_secret']`, normally sourced from an environment variable — this keeps the agent core-only and prevents secret export through Drupal configuration.
- 2026-11-03 — The two local demo clients are Drupal multisites within the main DDEV project, sharing code but using separate hosts, databases, files, configuration, and generated gitignored secrets — this gives realistic independent endpoints while keeping setup lightweight and idempotent with one `ddev start`.
- 2026-11-03 — Cron queues one item per active Site; the signed agent status request doubles as the uptime probe, with every attempt stored in `hm_uptime_check` and only valid 2xx payloads creating append-only Snapshots — one request measures real Drupal availability and collection health without redundant traffic.
- 2026-11-05 — Drupal.org release-history responses are normalized behind `ReleaseDataClientInterface`; successful project data is cached for six hours, unavailable/error results for five minutes, and “available with zero releases” remains distinct from lookup failure — analyzers stay independent of XML/HTTP details and a transient upstream outage cannot resolve real findings.
- 2026-11-05 — Snapshot module entries carry `origin` (core/contrib/custom) and their drupal.org `project` when known; analysis keys Findings by Site + project machine name + type, evaluates only stable published releases compatible with the installed core, and lets security findings supersede regular updates — submodules map to the correct release feed while core/custom extensions are not mistaken for contrib projects.
- 2026-11-05 — Finding reconciliation is evidence-conservative: an unavailable release feed preserves existing findings, missing core-compatibility metadata does not prove a Drupal 12 blocker, and removed-project findings resolve only from a snapshot with complete provenance — transient or incomplete evidence cannot silently clear or invent alerts.
- 2026-11-05 — Site health starts at 100 and subtracts capped finding penalties (security 30 each/60 max, unsupported 15/30, D12 blocker 10/20, regular update 5/20) plus up to 30 points proportional to failures in the latest 12 uptime checks; the result is floored at zero and missing uptime history adds no penalty — urgent operational/security work dominates, repeated minor findings cannot consume the entire score, and the formula remains deterministic and explainable.
- 2026-11-05 — `hm_agent` reads Upgrade Status's `upgrade_status_scan_results` key/value collection only when that module is enabled and emits a bounded version-1 summary with explicit not-installed/never-scanned/available/stale/failed states; scans are stale after 30 days and only fresh results targeting Drupal 12 reconcile scan-backed blockers — the agent stays core-only, supports Upgrade Status 4.3/5.x storage, and incomplete evidence never clears alerts.
- 2026-11-05 — Findings carry an evidence source (`release_data` or `upgrade_status`); release compatibility and local code scans reconcile independently, while a release-data D12 blocker suppresses a duplicate scan-backed blocker for the same project — distinct evidence retains safe lifecycle semantics without showing duplicate blockers.
- 2026-11-11 — The fleet dashboard is a permission-protected controller that maps Site/Finding entities into schema-validated theme SDC props and carries entity/list cache tags; HTMX will replace bounded dashboard fragments built from the same render path — presentation remains reusable and deterministic while asynchronous refresh cannot drift from the full-page output.
- 2026-11-11 — Client reports persist as append-only `hm_ai_report` entities; PHP calculates effort from open Findings, while Drupal AI with Anthropic writes only validated summary, release-digest, and Drupal 12 prose from JSON-encoded evidence. The Anthropic credential is a Key entity backed by `ANTHROPIC_API_KEY`, and the model is configuration (`claude-sonnet-5`) — reports remain auditable and testable, prompt injection is treated as untrusted data, exact evidence is never invented, and no secret enters configuration or Git.
- 2026-11-11 — Railway first-install detection may run `site:install` only after a direct database query proves the selected schema has zero tables; a failed Drupal bootstrap with any existing table aborts the deployment. Production images also normalize web-root modes to directories 0755/files 0644 — deployment input permissions or a bootstrap regression can no longer turn into an unreadable image or destructive reinstall.
- 2026-11-12 — Use stable MCP 1.2.3 with security-fixed Simple OAuth 6.1.4; group custom plugins under `list`, `get`, and `generate` so MCP's prefixing produces the four blueprint tool names exactly, disable every broad contributed tool group, and authorize them through a dedicated `mcp_client` role plus the `health_monitor:mcp` permission scope — the public surface is explicit and least-privilege, while all fleet logic remains in typed deterministic services shared with the Drupal UI.
